# Chapter 01 — Schema Overview & Data Strategy

## The G.O.D.S Data Philosophy

The G.O.D.S database is not just a persistence layer. It is a governance artefact. Every table, every column, every constraint is designed around the principle that **data serves governance, and governance requires complete, accurate, unalterable records**.

---

## Schema Domains

The database is organised into seven schema domains. Each domain owns a set of tables. Cross-domain foreign keys are permitted but must be explicitly documented.

| Domain | Schema | Tables |
|--------|--------|--------|
| Identity & Access | `iam` | `users`, `roles`, `role_assignments`, `permissions`, `sessions` |
| Governance | `governance` | `decisions`, `oversight_cases`, `operator_actions`, `model_registry` |
| Audit | `audit` | `audit_refs`, `merkle_roots`, `event_log` |
| SETHS | `seths` | `learners`, `students`, `employers`, `opportunities`, `applications`, `employees`, `timesheets`, `documents` |
| MADIBA | `madiba` | `institutional_milestones`, `capital_cycles`, `investor_profiles` |
| TS Industries | `ts` | `ts_projects`, `division_records`, `sector_participants` |
| Platform | `platform` | `tenants`, `saas_clients`, `policy_packs`, `policy_rules`, `knowledge_docs` |

## Universal Design Rules

Every table in the G.O.D.S database follows these rules without exception:

### 1. UUID Primary Keys

```sql
id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

No sequential integers as primary keys. UUIDs are:
- Safe to generate client-side (no round trip to get the ID before the insert)
- Safe to expose in URLs (no enumeration attacks)
- Globally unique (safe for distributed systems and future multi-tenancy)

### 2. Audit Timestamps

Every table has:
```sql
created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
created_by UUID REFERENCES iam.users(id),
updated_by UUID REFERENCES iam.users(id)
```

`updated_at` is maintained by a trigger — it is not the application's responsibility.

### 3. Soft Deletes

No hard deletes in production. Every table that represents a governed entity has:
```sql
deleted_at TIMESTAMPTZ,
deleted_by UUID REFERENCES iam.users(id),
deletion_reason TEXT
```

A soft-deleted record is excluded from normal queries via a partial index or query filter. It remains in the database permanently. The deletion event is recorded in the audit chain.

**Exception:** Tables that are append-only by design (audit records, event log) do not have soft delete columns — they have no delete operation at all.

### 4. Row-Level Tenant Isolation

Every table that holds data for multiple tenants has:
```sql
tenant_id UUID NOT NULL REFERENCES platform.tenants(id)
```

Every query that accesses tenant data must include `WHERE tenant_id = $current_tenant_id`. This is enforced by the service layer and by Row-Level Security (RLS) policies in PostgreSQL.

### 5. Audit Reference

Every write operation that is subject to audit (which is most of them) stores a reference to its audit record:
```sql
audit_ref_id UUID REFERENCES audit.audit_refs(id)
```

This creates a bidirectional link between the operational record and the audit chain.

## The Immutability Stack

G.O.D.S maintains three levels of data immutability, each progressively stronger:

| Level | Storage | Immutability Mechanism | Use Case |
|-------|---------|----------------------|---------|
| Soft | PostgreSQL | Soft delete + audit trail | Most operational records |
| Hard | PostgreSQL + Cassandra | Cassandra WORM write | Audit refs, decisions, oversight cases |
| Cryptographic | Cassandra + Merkle | HMAC seal + Merkle inclusion proof | Complete audit chain |

## Migration Strategy

Database migrations use Alembic. Each migration:
1. Has a unique revision ID (auto-generated by Alembic)
2. Has a description that explains what it changes and why
3. Has a tested downgrade path (unless it introduces a permanent structural change, in which case the downgrade is documented as "not applicable")
4. Is reviewed by a second developer before merging
5. Is run automatically by CI on the test database before merging

Migration files are stored in `platform-core/alembic/versions/`.

**Production migration procedure:**
1. Deploy new code (with backwards-compatible schema changes only)
2. Verify deployment is healthy
3. Run migration: `alembic upgrade head`
4. Verify migration success
5. Deploy any follow-up code changes that depend on the new schema

Never deploy a code change and its schema migration simultaneously. Always deploy schema first (or code that is backwards-compatible with both old and new schema).
