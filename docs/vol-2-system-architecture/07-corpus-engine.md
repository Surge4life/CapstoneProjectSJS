# Chapter 07 — Corpus Engine

## Purpose

The Corpus Engine manages the institutional knowledge base that powers G.O.D.S Intelligence. It handles document ingestion, chunking, embedding, storage, and retrieval. It is the librarian of the institutional intelligence system.

---

## Location

- **Router:** `platform-core/app/routers/intelligence.py` (corpus sub-routes)
- **Service:** `platform-core/app/services/gods_intelligence.py`
- **Service:** `platform-core/app/services/client_knowledge.py` (tenant corpora)
- **Model:** `platform-core/app/db/models/documents.py` — `KnowledgeDoc`
- **Storage:** OpenSearch (vector embeddings + full text)

## Document Lifecycle

```
Upload → Validate → Extract text → Chunk → Embed → Store → Index
                                                              ↓
Query ←────────────────────── Retrieve ←────── Vector search ←┘
```

### Step 1: Upload and Validate

Every document upload is validated for:
- File type (PDF, DOCX, TXT, MD supported)
- File size (max 50MB per document)
- Evidence tier declaration (uploader must state the tier)
- Upload permission for the declared tier

### Step 2: Text Extraction

| Format | Extraction Method |
|--------|-----------------|
| PDF | `pdfminer.six` — text layer extraction; falls back to OCR (Tesseract) for scanned PDFs |
| DOCX | `python-docx` — paragraph and table extraction |
| TXT | Direct read |
| MD | Direct read (Markdown stripped for embedding, preserved for display) |

Extraction quality is logged. Documents where extraction yields < 100 words are flagged as `low_extraction_quality` and require manual review before being made available for retrieval.

### Step 3: Chunking

Documents are split into semantic chunks for embedding. The chunking strategy:

```python
CHUNK_SIZE = 512      # tokens
CHUNK_OVERLAP = 64    # tokens — overlap preserves context at boundaries
```

Chunks are created at natural paragraph/sentence boundaries where possible. Tables and code blocks are kept as single chunks regardless of size.

Each chunk stores:
- `chunk_id` — UUID
- `doc_id` — parent document UUID
- `chunk_index` — position within document
- `text` — raw text of the chunk
- `embedding` — vector representation (1536 dimensions, OpenAI ada-002 compatible or local model)
- `tier` — inherited from parent document

### Step 4: Embedding

Embeddings are generated by the configured embedding model. In production, this is configurable:
- **Cloud mode:** OpenAI `text-embedding-ada-002` (via optional external consultation config)
- **Air-gap mode:** Local embedding model (e.g., `all-MiniLM-L6-v2` via sentence-transformers)

The embedding model is declared in the deployment configuration. All chunks in a corpus use the same embedding model. Changing the embedding model requires re-embedding the entire corpus.

### Step 5: Storage and Indexing

Chunks are stored in two places:
1. **OpenSearch:** Full-text index + vector index (k-NN plugin) for retrieval
2. **PostgreSQL:** `KnowledgeDoc` table for metadata, access control, and audit linkage

## Retrieval

Retrieval uses a hybrid approach:

```python
async def retrieve(query: str, tenant_id: UUID, top_k: int = 10) -> list[Chunk]:
    query_embedding = embed(query)

    # Vector search (semantic similarity)
    vector_results = await opensearch.knn_search(
        index=f"gods_corpus_{tenant_id}",
        vector=query_embedding,
        k=top_k * 2  # Over-fetch for reranking
    )

    # BM25 full-text search (keyword matching)
    keyword_results = await opensearch.match_search(
        index=f"gods_corpus_{tenant_id}",
        query=query,
        size=top_k * 2
    )

    # Reciprocal Rank Fusion — combines both result sets
    fused = rrf_merge(vector_results, keyword_results)

    # Apply evidence tier weighting
    tier_weighted = apply_tier_weights(fused)

    return tier_weighted[:top_k]
```

The hybrid approach outperforms pure vector search on factual queries (where exact term matching matters) while maintaining strong performance on semantic queries.

## Corpus Governance

The corpus is not a free-for-all. It has its own governance:

- **Upload audit:** Every document upload is recorded in the audit chain
- **Tier verification:** Tier 1 and 2 documents can be contested by a compliance officer
- **Version tracking:** Updating a document creates a new version; old versions are retained
- **Access control:** Each corpus is scoped to a tenant; cross-tenant retrieval is blocked at the service layer
- **Query audit:** Every retrieval query and its results are logged (not the user's query text — only the metadata: query_id, timestamp, top_k sources returned, confidence)
